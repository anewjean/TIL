### Today I Learn 25.07.12

#### 나만무
 - 트러블 슈팅
    * **api 라우팅 충돌**
      * `path variable`이 맨 마지막에 오는 경우, 같은 Prefix를 공유하는 다른 API들과 충돌하여 FastAPI가 올바르게 라우팅하지 못하는 문제가 있었다.
      * 구체적으로 `POST /api/workspaces/{workspace_id}/tabs`에 요청을 보냈는데 tab_id를 찾지 못 했다는 에러였다. 원인은 FastAPI가 같은 prefix를 가진 뒤쪽 경로로 잘못 매칭을 시도해 `POST /api/workspaces/{workspace_id}/tabs/{tab_id}`와 충돌했기 때문이다. 

      * FastAPI는 `/tabs/{tab_id}`처럼 **동적 path parameter가 있는 구체적인 경로를** `/tabs`와 같은 **정적 경로보다 먼저 매칭**시킨다. 이 때문에 `/tabs` 요청을 `/tabs/{tab_id}` 요청으로 오인하여 `{tab_id}`를 찾지 못했다는 에러가 발생한 것이었다. 
      * 이를 해결하기 위해서는 **FastAPI가 선언된 api 순서대로 처리**한다는 점을 이용해 `/tabs`를 `/tabs/{tab_id}`보다 먼저 선언하거나 명확한 suffix를 부여하는 방법이 있는데, 우리는 후자를 택해서 `POST /api/workspaces/{workspace_id}/tabs/{tab_id}`를 `POST /api/workspaces/{workspace_id}/tabs/{tab_id}/info`로 변경했다. (근데 좀 suffix가 구린 것 같다. suffix를 고친 후에 FastAPI가 api를 선언된 순서대로 처리한다는 사실을 알게됐다.)

    * **두 번째 요청부터는 Http-only Cookie에서 refresh token이 사라짐**
      * 우리는 refresh token을 Http-Only Cookie에 저장한다. 로컬 환경에서는 문제가 없었지만, 배포 서버에서는 두 번째 요청부터 쿠키에서 refresh token이 사라지는 문제가 발생했다. 원인은 HTTPS가 아닌 HTTP 프로토콜로 배포되었기 때문이었다. Http-Only 쿠키는 보안상 HTTPS 환경에서만 제대로 작동하기 때문에 이 설정이 없으면 브라우저가 쿠키를 저장하지 않는다는 사실을 알게 되었다.

    * **DB 정합성**
      * 조인 테이블이 많은 구조인데, 한 팀원이 반복적으로 더미 데이터를 잘못 입력해 쿼리 결과가 누락되거나 관계가 꼬이는 문제가 발생했다.
      * 처음에는 코드 문제로 의심했지만, 실제 원인은 'DB 간의 참조 무결성'이 보장되지 않아 정상 동작하던 api 응답이 500 에러가 났던 것이다.  
      * 이러한 문제를 대응하고자 다음과 같은 개선책을 적용했다.

        * **FK(Foreign Key) 제약조건과 `ON DELETE CASCADE`, `ON UPDATE CASCADE` 도입**  
          → 부모 데이터가 삭제되거나 변경되었을 때 자식 데이터가 자동으로 정리되도록 하여 참조 무결성(Referential Integrity)을 데이터베이스 수준에서 강제
          → 실수로 삭제된 유저가 workspace_members에 남아 있거나, 삭제된 탭 ID를 messages에서 참조하는 등의 '고아 레코드 문제' 해결
        
        * **문제가 발생하면 테이블 초기화 후 시드 데이터 자동 삽입 기능 추가**  
          → 매 테스트/로컬 실행 시마다 일관된 초기 상태를 유지해, 더미 데이터 삽입 실수를 줄이고 테스트 환경 신뢰성 확보
        
        * **전역 validation 도입 (API 단에서 유효한 foreign key 존재 여부 확인)**  
          → 데이터베이스 무결성과는 별도로, api 요청 시점에서 논리 오류를 사전에 차단
